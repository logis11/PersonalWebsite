While I was studying binary exploitation, there was constant mention of virtual memory or race conditions. Also, when learning tcache poisoning, I faced the concept of threads, and when I was learning more about kernel vulnerabilities, I faced the concept of page tables. Although there was no specific issue with triggering vulnerabilities, I noticed learning the operating system would be valuable knowledge for both deepening my understanding of why some features exist despite risking potential vulnerabilities and helping me understand new concepts. After searching for a suitable book for me, I found OSTEP (Operating Systems: Three Easy Pieces), which was free and had an adequate difficulty level for me. It has three big chapters, which are virtualization, concurrency, and persistence, and I have read through the first two chapters, as I felt they are more related to potential vulnerabilities. The remaining post will briefly go over the virtualization and concurrency parts of OSTEP, and how they may apply to some vulnerability concepts.

## Virtualization

The first few chapters of virtualization discuss how the CPU works. The operating system virtualizes the CPU, meaning each process (or thread) can assume it holds its own CPU. Meaning, they do not need to consider the task being interrupted by another task. Think about when you are playing a video game while watching YouTube (although that will be quite distracting). Even if you are using a single CPU, or a single-core system, two processes will look like they are both running concurrently, even though the CPU can only execute one instruction at a time (yes, there could be pipelining, but technically there is only one instruction at a given execution stage). Thus, the operating system supports task switching, where it stops the process that is using the CPU and lets another process use the CPU.

Before going further, a process is basically a running instance of a program. Since most conventional desktops or laptops use von Neumann architecture, meaning instructions and data use the same memory space (and yes, we still use modified Harvard structures for things such as i-caches), memory will contain a process's instructions, data, stack, and heap sections. Then, the CPU will read instructions and use the heap and stack as needed. When using stacks or computing, registers will also be used. Although stacks and instructions are all loaded in memory, registers are unique to the CPU. Meaning, different processes can have their own stacks, but their register states need to be saved and restored when they share the same CPU.

Thus, when a context switch is happening, register values need to be backed up, and new register values need to be set while switching to another process's execution context. Usually, those backed-up register values are stored in kernel-managed structures, often involving the kernel stack. Speaking of the kernel stack, it is important to recognize how there are kernel-side and user-side areas in memory. The kernel could be interpreted as a large library that every process uses (although it is a bit more than that nowadays, but historically the comparison makes some sense). This means kernel code also needs to exist somewhere in memory. In modern systems, kernel memory and user memory are logically separated, and a user process cannot directly access kernel-protected memory. If it attempts an invalid access, the CPU raises an exception, which may eventually result in something like a segmentation fault for the process.

This is a good time to also mention system calls. A system call is a method for a user program to request a service from the kernel. Although a user cannot directly call arbitrary kernel functions, it can do something called a system call. When a system call occurs, the kernel looks at the user's registers as input (and memory if necessary), and certain instructions are executed under kernel privilege. Note that access or authority checks are done on the kernel side, as if the check is done only on the user side, it can be forged very easily. If you have a good sense (or if you have prior knowledge), you may wonder if there is a method for tricking the access check. In a simple answer, the permission-checking algorithm itself cannot normally be modified by a user. However, if you somehow manage to forge or corrupt a credential or another security-relevant object that the kernel trusts, that may lead to LPE (Local Privilege Escalation) or EoP (Escalation of Privilege). Often, if you find a vulnerability in userland, one possible result is RCE (Remote Code Execution), which is executing arbitrary code under that specific user's privilege. Meaning, even if you manage to somehow trigger RCE, if the user cannot do any meaningful privileged action, the damage may not be as large as achieving code execution under SYSTEM- or root-level privilege.

We went a bit off track, but let's get back to virtualization. Since the operating system does context switching for users, when programming something, developers do not need to write code like if the process is kicked out of the CPU, do this. However, there needs to be a policy for when to execute a context switch. So, there is a CPU scheduling algorithm. But before discussing further, how can the operating system get ownership of the CPU? Since the OS is not like a normal user process (if you want to talk about how some features like daemons may act like processes, you are too advanced), you cannot rely only on the scheduler to somehow give the OS its CPU. In fact, how can you perform a context switch for scheduling if you do not first give control back to the kernel?

Historically, one of the methods was waiting for the user's process to use a system call. Since a system call transfers control from user mode to kernel mode, the OS can then decide what to do next. But in the past, when a single CPU was shared with other users, a user might just write code where it never calls a system call and monopolize the CPU. Also, it could be unfair for some processes that call system calls frequently, such as programs performing frequent I/O. Most user-space I/O eventually requires interaction with the kernel through system calls or related kernel interfaces. However, since one of the reasons why the OS is not just a library is due to its active resource management, a timer interrupt was created. It interrupts the CPU every given amount of time and forcefully gives the OS control. Then, the OS can look at the current situation and judge what to do. In the context of scheduling, it follows the scheduling algorithm that is currently set.

There is an MLFQ (Multi-Level Feedback Queue), which can avoid starvation through mechanisms such as priority boosting (and it is a lot more than that. To explain every feature, an entire post could be needed), lottery scheduling, and so on. Also, multi-CPU scheduling differs from single-CPU scheduling due to some caching features and CPU affinity. In short, thanks to the scheduling system that the OS provides, every process can act like it owns its own CPU.

There is also virtualization of memory. When doing binary exploitation, if ASLR is turned off, you often see instructions and data appearing at predictable virtual memory locations. However, what if there are multiple processes that want to use the same memory location? Or do they need to consider other processes and recompute where to allocate their data? The answer is no. Due to the virtualization of memory, each process can assume it has its own virtual address space.

Before getting deeper into it, you may have heard of PIE (Position Independent Executable). Although this was not invented purely for security purposes, PIE allows the executable itself to be loaded at different virtual memory locations. With ASLR turned on, this results in attackers not being able to easily guess where specific code or data is located. Related to this is PIC (Position Independent Code), which means code is written in a way that allows it to execute correctly regardless of where it is loaded. Shared libraries such as `.so` files commonly use position-independent code because different processes may load the same library at different virtual addresses. If a file uses fixed absolute addresses everywhere, loading it at different positions becomes difficult. Thus, position-independent code uses things such as relative addressing, including addresses relative to the program counter (`rip`/`eip` depending on the architecture), so code can be loaded at different locations in virtual memory. PIE is basically applying this idea to the main executable as well.

Anyways, virtualization of memory is done using page tables. A page table is basically a data structure that maps virtual pages to physical pages. This means two processes can use the exact same virtual address while actually referring to completely different locations in physical memory. For example, process A and process B could both have something at `0x400000`, but the address may map to completely different physical pages for each process. This is why every process can somewhat act like it owns the entire memory space without caring too much about what another process is doing.

But now there is another problem. If the CPU needs to look through the page table every time it accesses memory, it will obviously be quite slow. Remember that even reading an instruction requires memory access. So the CPU has something called a TLB (Translation Lookaside Buffer), which basically stores recently used virtual-to-physical address translations. If the translation is already in the TLB, the CPU does not need to perform the full page-table lookup again.

Now, what happens if a process tries to access a page that is not currently available in physical memory? This is where a page fault happens. The CPU cannot complete the access using the current page-table state, so it transfers control to the kernel and lets the kernel figure out what happened. Sometimes this is completely normal. Maybe the process has a valid virtual page, but the physical page has not been allocated yet. Maybe the page was previously moved out of RAM. On the other hand, if the process is trying to access an address it is not allowed to access, such as an unmapped page or a page with invalid permissions, the kernel may eventually send `SIGSEGV`. So when you see a segmentation fault while doing exploitation, there was usually some memory-access fault underneath it, but not every page fault means your program is going to crash.

You may have seen `malloc()` a lot if you have coded in C. Also, you may think `malloc()` is some sort of system call since it seems like the OS is the one in charge of accessing memory. However, if you read the malloc source code (and I highly recommend doing so), you can realize that `malloc()` itself is just a library function, and the practical system calls used to obtain more memory are things such as `brk`/`sbrk` or `mmap`. After gaining a chunk of memory from the OS, the allocator library is the one distributing smaller chunks to your program. This is also why things like bins, chunks, tcache, and allocator metadata even exist in the first place. The kernel does not manage every single `malloc(0x30)` for you.

Also, just because the process requested some virtual memory does not necessarily mean all of that memory immediately occupies physical RAM. Physical pages can be allocated when they are actually accessed. And if the system starts running low on physical memory, some pages can be swapped out. Swapping out basically means moving the contents of a page from RAM to a storage-backed swap area so that the physical frame can be used for something else. If the process tries to use that page again later, a page fault occurs, the kernel brings the page back into RAM, updates the mapping, and lets the process continue. Of course, this is much slower than simply accessing RAM, which is why excessive swapping makes a system painfully slow.

Then you may think a process can have an extremely huge virtual address space. If every possible page needs its own entry in one giant page table, wouldn't the page table itself take up a ridiculous amount of memory?

Yes, and this is why a simple linear page table does not scale very well. A process usually does not use every address from the bottom to the top. There may be code somewhere, heap somewhere else, shared libraries somewhere else, and stack near the top, while huge ranges in between are unused. If we had one giant linear table with an entry for every possible virtual page, we would waste a lot of memory just storing entries for addresses that are never used.

So modern systems use multi-level page tables. Instead of having one huge table, the virtual address is divided into multiple parts, and each part is used to find the next level. If a huge region of virtual memory is unused, the lower-level tables for that region do not even need to exist. This makes page tables much more practical for sparse address spaces.

Then how does the CPU know which page table belongs to the currently running process? There are architecture-specific registers for this. On x86, for example, `CR3` is used to point to the root of the current page-table hierarchy. So when the OS switches from one process to another, changing the execution context may also involve switching the address-space context. This is why the exact same virtual address can suddenly map somewhere completely different depending on which process is currently running. There are also various TLB optimizations because simply throwing away every cached translation on every process switch would be quite expensive, but we do not need to go that deep here.

## Concurrency

Now concurrency chapter. Concurrency chapter is all about managing shared resources through threads. First, we need to understand what a thread is. You may think of it somewhat like a process with two PCs going on. They share the same page table, meaning they are using the same virtual address space and can therefore access the same mapped physical pages, variables, heap, and so on. The main difference is that different instructions of the process can be executed by each thread, while they also have separate execution states such as registers and stacks.

If you have learned heap exploitation, you may realize that tcache literally stands for thread cache. Tcache is managed per thread, while other allocator structures can be shared across threads. Its per-thread state is associated with thread-local storage, which is one of the reasons why tcache behaves differently when multiple threads are involved. This is also an example of how something that looks like just an allocator implementation detail is actually related to the OS concept of threads.

This may seem like a very useful feature, but think about a scenario where two threads are simply doing:

`counter = counter + 1`

You may think the final value should obviously increase twice. But this single line is not necessarily a single CPU operation. It may first load `counter` into a register, add one, and then write the value back into memory. So let's say `counter` is 10. Thread A reads 10. Before it writes the result back, thread B also reads 10. Thread A adds one and writes 11. Then thread B also adds one to the value it already read and writes 11. You expected 12, but the result is 11.

This is a race condition. The result depends on the timing and ordering between multiple threads. This is also why race conditions can be annoying to debug. You may run the program a hundred times and nothing happens, and then one specific scheduling order suddenly breaks everything.

This is where locks come in. A mutex can be used so that only one thread accesses a critical section at a time. A thread locks the mutex, accesses or modifies the shared resource, and then unlocks it. Other threads trying to use the same mutex have to wait. A semaphore is somewhat similar, but instead of simply allowing only one thread, it maintains a counter, so it can be useful when multiple instances of a resource are available.

However, there is another question. How do you even implement the lock itself? If you simply write something like:

`if (lock == 0) lock = 1;`

you have the exact same problem again. Two threads may both see zero before either of them changes it. So CPUs provide hardware-level atomic operations, such as compare-and-swap, where an operation can be performed without another CPU observing some broken intermediate state. Mutexes, spinlocks, and many other synchronization primitives are eventually built using these kinds of atomic hardware operations.

This is also where race conditions become interesting from the vulnerability perspective. A famous example is Dirty COW, a Linux kernel vulnerability. COW stands for Copy-On-Write. Let's say two mappings can share the same physical page because neither one needs to modify it yet. There is no reason to make another copy immediately. If one of them later tries to write to the page, the kernel can create a private copy for that writer. This saves unnecessary memory and copying.

Dirty COW happened because there was a race condition involving this Copy-On-Write behavior and concurrent memory operations. Under a specific timing, an unprivileged process could end up modifying memory that was supposed to remain read-only. This is a good example because none of the individual features are particularly weird. Copy-On-Write is normal, page faults are normal, and concurrent memory operations are normal. The vulnerability appears because their interactions allow a state that was not supposed to happen.

There is also a related concept called TOCTOU, or Time Of Check To Time Of Use. Imagine a privileged program first checks whether a file is safe and then uses that file. If an attacker can change what that path refers to between the check and the actual use, the program may end up using something different from what it originally checked. A lot of TOCTOU vulnerabilities are race conditions because the attacker is trying to win that timing window. The important idea is that the program checked some state at one moment and assumed that the state would still be the same later.

Interestingly, similar patterns can also appear outside of traditional OS vulnerabilities. Even in something like an LLM application, some data or resource may first be checked under one context, but a changed or differently resolved version may later be used when a privileged action is actually performed. I would not call every one of those a literal TOCTOU vulnerability, but the general mistake is somewhat similar. Something was trusted because of an earlier check, while the thing being used later is not necessarily guaranteed to be the exact same thing.

There is also event-based concurrency. Event-based programming is somewhat like having a single thread going on, so you often do not need locks for code running on the same event loop. Instead of multiple threads executing different instructions at the same time, the program counter moves through different event handlers while the runtime somehow remembers where previous operations left off. When an I/O operation finishes or some event happens, the program continues the corresponding work later. A server written with Node.js is a good example of this kind of model. Of course, this does not mean event-based programs can never have concurrency bugs, but it avoids many of the traditional shared-memory locking problems that come with multiple threads.

So this is everything from virtualization to concurrency, briefly summarized. They may not be directly connected to vulnerabilities or binary exploitation, but it is still quite useful to understand how the OS works in general. How can you say you are exploiting something if you do not know how it really works?
